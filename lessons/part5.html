Lesson 1: Python Fundamentals

Python is a programming language, a way of giving a computer clear, step-by-step instructions using text instead of clicking buttons. There's no menu to click. You write exactly what you want, and Python does it.

A variable is a labeled box for storing information, like price = 200. Data types include numbers, text, and True or False values. Operators handle maths and comparisons. Conditionals, if, elif, else, make decisions, the same job Excel's IF and SQL's CASE did. Loops repeat an action automatically. Functions are reusable blocks of instructions you can call by name.

Let's write our first real check on the shop. Remember Meat Pie's "Needs attention" flag from SQL's CASE statement back in Part 3?

units_sold = 8
if units_sold >= 15:
    print("Strong seller")
elif units_sold >= 10:
    print("Steady seller")
else:
    print("Needs attention")

Run this with Meat Pie's original 8, and Python prints "Needs attention," the exact same result the SQL CASE statement gave you, just written in a different language.

Now you try it

  1. Change units_sold to 20, Coke's number, and work out by hand which branch of the if/elif/else would print.
  2. Write a small loop (on paper, or in a notebook if you have Python installed) that prints "Strong seller," "Steady seller," "Steady seller," and "Needs attention" for the four values 15, 20, 12, 8, one per line, without repeating the if/elif/else block four separate times.
  3. Compare this Python if/elif/else to the SQL CASE statement from Part 3, Lesson 3. What's structurally the same about them?

The takeaway

Every Python skill you'll learn builds from a handful of core ideas: variables, conditions, loops, and functions. You already used the same logic in Excel and SQL. Python just writes it differently.

Lesson 2: Working with Data, NumPy and Pandas

Plain Python is great, but it wasn't built specifically for data. Two add-on libraries, NumPy and Pandas, turn Python into a serious data analysis tool. Pandas introduces the DataFrame, essentially a spreadsheet living inside Python, and it can read CSV, Excel, or SQL data directly with one line of code.

Let's load our snack shop into Python properly:

import pandas as pd

data = {
    "name": ["Chin Chin", "Coke", "Meat Pie", "Fanta"],
    "type": ["Snack", "Drink", "Snack", "Drink"],
    "price": [200, 150, 300, 150],
    "units_sold": [15, 20, 8, 12]
}
df = pd.DataFrame(data)
print(df)

This builds the exact same four-row table we've used since Part 1, now as a Pandas DataFrame, ready for everything that comes next in this part.

Now you try it

  1. Run (or trace through by hand) df.head() on this DataFrame. How many rows would it show, given the table only has four?
  2. Write the line of code that would calculate revenue for each row (price times units_sold), the same calculation you first did in Excel's Lesson 2.
  3. If you had our shop's data in a CSV file instead of typed directly into Python, what one line of code would load it into a DataFrame called df?

The takeaway

A Pandas DataFrame is the Python equivalent of an Excel spreadsheet or a SQL table. Everything you already know from Parts 2 and 3 has a matching idea here, just written in code instead of formulas or queries.

Lesson 3: Data Cleaning and Preparation with Pandas

Just like in Excel and SQL, real data almost always needs cleaning before you can trust it. Pandas handles this with a few lines of code.

df.info() and df.describe() give quick overviews. df.dropna() removes missing rows, df.fillna(value) fills them in instead. df.drop_duplicates() removes duplicate rows. And string methods handle the same messy-text problem we've now fixed three times, in Excel with TRIM and PROPER, and in SQL with TRIM and UPPER.

df["name"] = df["name"].str.strip().str.title()

This strips extra spaces and capitalizes each word, so " meat pie" and "Meat Pie" both become "Meat Pie," the exact same fix, the third time, now in Pandas.

Now you try it

  1. If our shop's units_sold column had a missing value for one row, would df.dropna() or df.fillna(0) be more appropriate here? Explain your reasoning.
  2. Write the line of code that would remove exact duplicate rows from our DataFrame.
  3. Compare df["name"].str.strip().str.title() to PROPER(TRIM(A2)) from Excel and UPPER(TRIM(name)) from SQL. All three solve the same problem; what's different about how each tool expresses it?

The takeaway

Garbage in, garbage out applies just as much in Python as it did in Excel and SQL. You've now fixed the exact same "Meat Pie" text problem three separate times, in three different tools, which is exactly the kind of pattern-recognition that makes you a stronger analyst.

Lesson 4: Data Transformation

Once your data is clean, you often need to reshape it: select specific parts, create new columns, combine tables, or summarize by group.

.loc[] selects by label, .iloc[] by position. You can create a new column directly, like df["revenue"] = df["price"] * df["units_sold"]. groupby is Pandas' version of SQL's GROUP BY. And merging two DataFrames together works like a SQL join.

Let's answer the same question three tools have now answered: total revenue by type.

df["revenue"] = df["price"] * df["units_sold"]
revenue_by_type = df.groupby("type")["revenue"].sum()
print(revenue_by_type)

This returns Drink at ₦4,800 (150×20 + 150×12) and Snack at ₦4,500 (200×15 + 300×8, using the original 8 units before correction), the same style of answer the Pivot Table gave in Excel and GROUP BY gave in SQL.

Now you try it

  1. Write the groupby line that would find the average price per type instead of total revenue.
  2. If you had a separate sales DataFrame like the one we built in SQL's Lesson 5, what Pandas function would you use to combine it with this snacks DataFrame, the same way JOIN did in SQL?
  3. Compare this groupby result to the Pivot Table from Excel and the GROUP BY query from SQL. Is the underlying logic the same across all three, even though the code looks different?

The takeaway

Excel Pivot Tables, SQL's GROUP BY, and Pandas' groupby are all doing the exact same job: summarizing data by category. Different tools, identical underlying idea, which is the whole throughline of this course.

Lesson 5: Exploratory Data Analysis in Python

Just like in Excel and SQL, you explore your data before drawing conclusions. Python makes this fast and repeatable, especially on datasets far larger than our four-row shop.

df.describe() gives count, mean, min, and max for every numeric column at once. df.corr() checks whether two numbers move together. df["column"].value_counts() counts how often each category appears.

print(df["type"].value_counts())
print(df["units_sold"].describe())

The first line shows 2 Snacks and 2 Drinks. The second gives you the same average, min, and max we calculated by hand back in Part 1, Lesson 7, and again with Excel's AVERAGE, MAX, and MIN functions in Part 2.

The takeaway

EDA in Python follows the exact same mindset as EDA in Part 1 and Excel. You're just doing it faster, and the real advantage shows up once your dataset grows far past four rows.

Lesson 6: Data Visualization in Python

Python has its own charting tools. The two most common are Matplotlib, the foundation, and Seaborn, built on top of it with nicer defaults.

import seaborn as sns
import matplotlib.pyplot as plt

sns.barplot(data=df, x="name", y="units_sold")
plt.title("Snack Shop: Units Sold")
plt.show()

Three lines of code, and you get the same bar chart you first built by hand in Part 1, then in Excel's Insert menu in Part 2. Coke's bar is still the tallest, Meat Pie's still the shortest. The chart hasn't changed. Only the tool building it has.

Lesson 7: Introduction to Statistics with Python

Remember statistics from Part 1: averages, medians, spread? Python lets you go a step further, checking not just what happened, but whether a difference is actually meaningful or just chance.

SciPy is a library with ready-made statistical tests. A hypothesis test is a formal way of checking whether an observed difference, like one group performing better than another, is likely real.

Imagine the shop owner tries a new pricing strategy for two weeks, and average daily units_sold rises from 13.75 (our original average) to 16. A hypothesis test could help answer: is that rise a real effect of the new pricing, or could it just as easily be random day-to-day variation with such a small sample?

Now you try it

  1. Using our original four units_sold values, 15, 20, 8, 12, which averaged to 13.75, why might a rise to 16 over just two weeks not be enough evidence on its own to declare the new pricing a success?
  2. What additional information (beyond just the average) would help you judge whether that rise was meaningful?
  3. Think of another two groups you could compare from something in your own life. What question would a hypothesis test help answer there?

The takeaway

Just because one number is bigger than another doesn't automatically mean the difference is real. Statistics helps you tell an actual pattern apart from random noise, especially with a dataset as small as our shop's four items.

Lesson 8: Working with Databases and APIs

So far we've mostly worked with data typed directly into Python. Real-world data often lives elsewhere, inside a company's database, or out on the internet through an API.

You can connect Python directly to SQL databases and run the exact queries you wrote in Part 3 from inside Python. An API lets one piece of software request data from another over the internet, and the requests library is Python's tool for fetching it.

import sqlite3
conn = sqlite3.connect("shop.db")
result = pd.read_sql("SELECT * FROM snacks WHERE units_sold > 10", conn)
print(result)

That's the exact SQL query from Part 3, Lesson 1, run from inside Python instead of a SQL client, returning the same Chin Chin, Coke, and Fanta rows.

  2. If you wanted to pull the average price per type using this connection, would you write that logic in SQL inside the query string, or in Pandas after loading the data? Is there a reason to prefer one over the other?
  3. Think of one piece of live data (weather, exchange rates, sports scores) you'd want to pull automatically. Why would an API suit that better than typing the data in by hand, the way we did for our snack shop?

The takeaway

A data analyst's skillset isn't limited to files someone hands you. SQL and APIs, both usable directly from Python, let you go get the data yourself, straight from its source.

Lesson 9: Automating and Reporting

Remember how Power Query in Excel and Power BI could remember your cleaning steps and repeat them automatically? Python does the same thing, with even more control, across your whole workflow.

You can turn a series of manual steps into a script you run anytime, and export results straight to Excel, CSV, or PDF.

df["name"] = df["name"].str.strip().str.title()
df["revenue"] = df["price"] * df["units_sold"]
df.to_excel("shop_report.xlsx", index=False)

Three lines: clean the names the way we've now done in three tools, calculate revenue, and save a ready-to-share Excel file, all in under a second, a task that would otherwise mean manually retyping formulas every time new sales data arrived.

  2. Where in this three-line script would you add a step to remove duplicate rows, and why does the order matter?

The takeaway

The real power of Python isn't just analysis. It's turning any repeatable task into something that runs itself, the same automation instinct you first met with Power Query, now with full control over every step.

Lesson 10: Version Control and Portfolio Readiness

We covered GitHub back in Part 1. Now let's apply it specifically to a Python project, since this is where your strongest portfolio piece is likely to come from.

A clear folder structure, a data folder, a notebooks folder, and a README file, makes a project easy for anyone to understand. Publishing means the code, explanation, and results are visible to a stranger scrolling through your profile.

Here's what a finished version of our own snack shop project might look like on GitHub:

snack-shop-analysis/

├── notebooks/
│   └── analysis.ipynb
├── README.md

The README would explain, in plain language, exactly what we did across this entire course: cleaned the data, explored it, modeled it, visualized it, and found that Drinks outsold Snacks 32 to 23 units, with Meat Pie needing attention. The same finding, first spotted in Part 1 by hand, now backed by real code across four different tools.
