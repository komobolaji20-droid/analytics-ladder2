Lesson 1: Introduction to Power BI and Navigating

If Excel is a notebook and SQL is a filing cabinet, Power BI is closer to a movie studio: a place where data becomes an interactive visual story people can click, filter, and explore themselves.

Power BI has three main views. Report view is where you build visuals. Data view shows your raw tables, similar to opening a spreadsheet. Model view is where you connect tables together. The usual order is to bring data in, clean it, connect the tables, then build visuals.

Let's bring our snack shop in. Import the snacks and sales tables we built in Part 3, the same snack_id, name, type, price on one side and sale_id, snack_id, units_sold on the other. In Data view, you'd see both tables looking almost exactly like they did in a SQL client. Switch to Report view, drag "name" and "units_sold" onto a blank canvas, and Power BI draws your first chart instantly, the same shop data, now interactive.

Now you try it

  1. If you have Power BI installed, import the snacks and sales tables and look at them in Data view. Do they look the way you'd expect from Part 3?
  2. Based on the description above, what do you think would happen if you tried to build a chart in Report view before connecting the two tables in Model view?
  3. Which of the three views would you open first if a colleague handed you a Power BI file you'd never seen before, and why?

The takeaway

Power BI isn't just "Excel with better charts." It's a complete system for connecting, modeling, and presenting data as one interactive experience, and our two small tables are enough to see all three views working together.

Lesson 2: ETL and Power Query in Power BI

Just like in Excel, Power BI uses Power Query to clean and prepare data before it ever reaches a chart. This process has a name: ETL, standing for Extract, Transform, Load.

Extract means pulling data in from a source. Transform means cleaning and reshaping it, removing errors, renaming columns, fixing data types. Load means bringing the cleaned data into Power BI's model, ready to use.

Remember the messy "Meat Pie" text problem from Parts 2 and 3, extra spaces and inconsistent capitalization? If our shop's sales data arrived in Power BI with that same problem, you'd fix it once inside Power Query, using a Trim step and a Capitalize Each Word step, exactly like the PROPER and TRIM combination from Excel and the UPPER and TRIM combination from SQL. The difference is that Power Query remembers the fix, and it reapplies automatically every time the file refreshes.

Now you try it

  1. In your own words, describe what "Extract, Transform, Load" would look like specifically for our shop's snacks and sales tables.
  2. If the sales table arrived with a typo like "20" recorded as "2O" (letter O instead of zero) for Coke's units, would that be caught during Transform, or would it need fixing earlier? Why?
  3. Compare the Power Query "clean once, refresh forever" approach to the Trim and Proper formulas from Excel Part 2, Lesson 3. What's the actual difference in effort over time?

The takeaway

Nothing in Power BI should touch raw, messy data directly. Everything passes through Power Query first, the same discipline you already practiced with our shop's data in both Excel and SQL.

Lesson 3: Data Preparation in Power Query

Now let's go deeper into what actually happens inside Power Query: the specific cleaning and shaping tasks that turn source data into something ready for analysis.

This includes removing unnecessary columns and rows, renaming columns to be clear and consistent, fixing data types so a date column is actually recognized as a date rather than text, and splitting or merging columns. Every change you make is recorded as a numbered, editable step, called the Applied Steps list.

Suppose our sales table arrived with a single column called "Sale Info" containing values like "3-Coke-20," combining the sale ID, snack name, and units sold into one messy string. In Power Query, you could split that one column into three clean columns in a couple of clicks, and that split would repeat automatically on every future file, the same way splitting "Full Name" into first and last name would work for a customer list.

Now you try it

  1. If our sales data arrived with prices stored as text, like "₦150" instead of the number 150, what step would you need in Power Query before any SUM or AVG calculation could work correctly?
  2. List the Applied Steps, in order, you'd expect after: importing the sales table, splitting the "Sale Info" column, then removing a blank row. Does order matter here?
  3. Why is having a recorded, editable list of steps more useful than just quietly fixing the data by hand each time?

The takeaway

Because Power Query remembers every step you take, data preparation becomes a one-time investment rather than a chore you repeat each time new sales data lands, whether that data comes from our snack shop or anywhere else.

Lesson 4: Data Modeling

This is one of the most important lessons in the entire Power BI journey. A data model is how your different tables relate to each other, like drawing a family tree that shows how everything connects.

A fact table holds measurable events, like individual sales transactions. A dimension table holds descriptive details about those events, like a list of products. The most common way to organize this is a star schema: one fact table in the center, surrounded by dimension tables connected to it. Cardinality describes how rows relate between two tables, and cross-filter direction controls which table's filters affect the other when you click on a chart.

Our own snack shop already fits this exactly. sales is the fact table: it holds the actual measurable event, units_sold, tied to a snack_id and a sale_id. snacks is the dimension table: it holds descriptive details, name, type, price, one row per snack. Connect them by snack_id, and you have a simple, correct star schema, one fact table and one dimension table.

Now you try it

  1. In our shop's model, which table is the fact table and which is the dimension table? Justify your answer using the definitions above.
  2. If the shop later added a customers table (customer_id, name, city) and each sale recorded which customer bought it, would customers be a fact table or another dimension table?
  3. Sketch (on paper) the star schema for our shop with all three tables: snacks, sales, and customers, showing which columns connect them.

The takeaway

A messy or missing data model is the number one reason beginners get confused, wrong, or duplicated numbers in Power BI. Our shop's model is about as simple as it gets, one fact table and one dimension table, and that simplicity is exactly what you should aim to preserve even as real projects grow larger.

Lesson 5: Introduction to DAX

DAX, short for Data Analysis Expressions, is Power BI's own formula language. It's similar in spirit to Excel formulas, but built to work across your entire data model rather than individual cells.

A DAX formula always starts by naming what you're creating, followed by an equals sign. Unlike an Excel formula sitting in one cell, DAX formulas are aware of your whole data model, including filters and relationships.

Let's write our first one, calculating total revenue across the shop:

Total Revenue = SUMX(sales, sales[units_sold] * RELATED(snacks[price]))

This single line pulls each sale's units_sold, multiplies it by that snack's price from the related snacks table, and adds it all up, giving the same ₦9,300 total we first calculated by hand back in Part 1. Once written, this measure can be dropped into any chart and will recalculate correctly no matter how the report gets filtered, by type, by snack, by date.

Now you try it

  1. Based on what you already know about SQL's SUM function from Part 3, describe in plain English what the DAX formula above is doing.
  2. Why does this formula need RELATED(snacks[price]) instead of just referencing a price column directly inside the sales table?
  3. If you filtered a report to show only Drinks, would this measure automatically recalculate to show just Drink revenue, or would it still show the full ₦9,300? Why?

The takeaway

DAX feels intimidating at first because it looks like a new language, but it borrows heavily from ideas you already know: SUM from Excel and SQL, and the relationships you just built in Lesson 4's data model.

Lesson 6: Calculated Columns, Measures, and Common DAX Functions

DAX gives you two different ways to add calculations to your model, and knowing which to use is one of the most important beginner skills in Power BI.

A calculated column creates a new column of data, calculated row by row and stored permanently in the table. A measure calculates a result on the fly, based on whatever is currently being viewed or filtered, and is more flexible and efficient. CALCULATE() is one of the most powerful DAX functions, letting you change the filter context of a calculation.

Let's build a measure for just Snack-type revenue:

Snack Revenue = CALCULATE([Total Revenue], snacks[type] = "Snack")

Using our shop's numbers, that returns the combined Chin Chin and Meat Pie revenue, ₦3,000 plus ₦2,400 (once Meat Pie's units_sold was corrected to 10 back in Part 3), for a total of ₦5,400. This measure automatically updates if it's added to a chart that's already filtered by date or by a specific snack, since CALCULATE is designed to layer on top of whatever filters already exist.

Now you try it

  1. Without writing real code, describe in plain English what a measure called Drink Revenue = CALCULATE([Total Revenue], snacks[type] = "Drink") would calculate.
  2. Would Snack Revenue plus Drink Revenue equal Total Revenue from Lesson 5? Why should that always be true if the model is built correctly?
  3. If you built Total Revenue as a calculated column instead of a measure, what would go wrong when someone filtered the report to just one snack type?

The takeaway

When in doubt, use a measure rather than a calculated column. Measures are more flexible, use less memory, and automatically respect whatever filters are applied to your report, exactly as we saw with Snack Revenue above.

Lesson 7: Building Reports and Visualizing Data

With the model built and DAX measures ready, it's time to build the actual report: the visual page people will interact with.

Reports can be single-page summaries, multi-page detailed reports, or paginated print-style reports. You drag fields and measures onto the canvas to create visuals: bar charts, line charts, cards for single big numbers, tables. Slicers are interactive filters that let the viewer explore the data themselves.

Let's build our shop's first report page. A card showing Total Revenue at the top, ₦9,300 in bold. Below it, a bar chart with "name" on one axis and units_sold on the other, the same comparison we first sketched by hand in Part 1. A slicer for "type," so the owner can toggle between Snack and Drink and instantly watch every visual on the page update, thanks to the relationships built in Lesson 4.

  2. If the owner clicks "Snack" on your type slicer, what should happen to the Total Revenue card, based on what you learned about CALCULATE in Lesson 6?
  3. What's one additional visual you'd add to this report using our shop's data, and what question would it answer?

The takeaway

A great Power BI report isn't just charts on a page. It's an interactive experience where the viewer can click, filter, and explore the data themselves, without needing you there to explain it, the same principle we first discussed with dashboards back in Part 1.

Lesson 8: Dashboard Design and Data Storytelling in Power BI

Remember the dashboard design principles and data storytelling lessons from Part 1? Now it's time to apply them directly, using everything Power BI gives you.

The same rules apply: keep it simple, use colour with purpose, put the most important number top-left, align everything neatly. Titles and short text boxes guide the viewer through the story instead of leaving them to guess. Related visuals get grouped together with consistent colours across the whole report.

Take our one-page report from Lesson 7 and add a title: "Snack Shop Performance Overview." Add a one-line summary text box underneath: "Drinks are outselling Snacks 32 to 23 units, with Meat Pie needing attention." That single sentence, sitting above the bar chart and card, tells the shop owner the whole story in five seconds, the exact non-technical storytelling skill from Part 1, Lesson 4, now embedded directly into the report itself.

Now you try it

  1. Write your own one-line summary sentence for our shop's report, using the actual numbers we've calculated throughout this course.
  2. Where on the report page would you place that summary sentence, and why does its position matter?
  3. If the shop owner only had five seconds to look at this report, which single element, the card, the chart, or your summary sentence, would you make sure they saw first?

The takeaway

A technically correct report that tells no clear story still fails at its real job. Every report should have one central message the viewer walks away remembering, the same message our shop's numbers have been building toward since Part 1.

Lesson 9: Publishing and Sharing

A Power BI report sitting only on your own laptop is exactly the "hidden project" problem from Part 1, Lesson 11. Nobody else can see it or use it. Publishing is how you make it truly usable.

The Power BI Service is the online platform where you publish reports so others can view them through a browser without Power BI installed. Data refresh schedules let a report automatically pull in new data on a schedule instead of manual refreshing. A report is a detailed, multi-visual page you build; a dashboard is often a simpler, pinned summary of your favourite visuals, useful for quick daily monitoring.

Publish our shop's report to the Power BI Service, and set it to refresh every morning at 6am. By the time the owner checks it over breakfast, the numbers already reflect the previous day's sales, without anyone touching a spreadsheet.

The takeaway

Just like the GitHub lesson taught you: the work isn't finished when it's built. It's finished when it's published, shared, and visible to the people who need it, whether that's a recruiter on GitHub or a shop owner checking their dashboard over breakfast.
