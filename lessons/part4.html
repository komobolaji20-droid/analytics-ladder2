🖥️ Lesson 1: Introduction to Power BI & Navigating

Let's start simple If Excel is a notebook and SQL is a filing cabinet, Power BI is like a movie studio — it's where you turn data into interactive visual stories that people can click, filter, and explore themselves.

Key Ideas - Power BI has three main views: Report view (where you build visuals), Data view (where you see your raw tables), and Model view (where you connect tables together) - You typically bring data into Power BI, clean it, connect your tables, then build visuals — in that order

A Simple Example You import a sales spreadsheet into Power BI. In Data view, you can see every row, just like Excel. Switch to Report view, and you can drag "Region" and "Sales" onto a blank canvas to instantly create your first chart.

🧠 Now You Try (Exercise) If you have Power BI installed, open it and explore the three views (Report, Data, Model) using any small spreadsheet. If not yet installed, write down what you think each of the three views is for, based on the explanation above.

✅ Big Idea to Remember Power BI isn't just "Excel with better charts" — it's a complete system for connecting, modeling, and presenting data as one interactive experience.

🔄 Lesson 2: ETL Workflow & Introduction to Power Query

Let's start simple Just like in Excel, Power BI uses Power Query to clean and prepare data before it's ever used in a chart. This process has a name: ETL — Extract, Transform, Load.

Key Ideas - Extract: pulling data in from a source (Excel file, database, website) - Transform: cleaning and reshaping it (removing errors, renaming columns, fixing data types) - Load: bringing the cleaned data into Power BI's model, ready to use

A Simple Example You connect Power BI to a messy sales CSV with inconsistent date formats. In Power Query, you fix the date format once — and every time the file updates, Power BI automatically repeats that same fix without you touching anything.

🧠 Now You Try (Exercise) Write out, in your own words, what "Extract, Transform, Load" would look like if you were preparing ingredients to cook a meal — matching each ETL step to a cooking step.

✅ Big Idea to Remember Nothing in Power BI should touch raw, messy data directly — everything passes through Power Query first, exactly like washing ingredients before cooking.

🧽 Lesson 3: Data Preparation in Power Query

Let's start simple Now let's go deeper into what actually happens inside Power Query — the specific cleaning and shaping tasks that turn messy source data into something ready for analysis.

Key Ideas - Removing unnecessary columns and rows - Renaming columns to be clear and consistent - Fixing data types (making sure a "date" column is actually recognized as a date, not text) - Splitting or merging columns (e.g., splitting "First Last" into two separate columns) - Every change you make is recorded as a numbered, editable step — this is called the "Applied Steps" list

A Simple Example A dataset has a column called "Full Name" with values like "Bolaji Zachariah." In Power Query, you can split this into "First Name" and "Last Name" in one click — and this split will automatically repeat every time new data is loaded.

🧠 Now You Try (Exercise) Think of a messy dataset you've seen before (even a school result sheet). List 3 specific cleaning steps you'd need to perform on it before it's ready for analysis.

✅ Big Idea to Remember Because Power Query remembers every step you take, data preparation becomes a one-time investment — not a chore you repeat every time new data arrives.

🧩 Lesson 4: Data Modeling

Let's start simple This is one of the most important lessons in the entire Power BI journey. A data model is how your different tables relate to each other — think of it as drawing a family tree that shows how everything connects.

Key Ideas - Fact Tables vs. Dimension Tables: A fact table holds the actual measurable events (e.g., individual sales transactions). A dimension table holds descriptive details about those events (e.g., a list of products, or a list of customers). - Star Schema: the most common way to organize a data model — one fact table in the center, surrounded by dimension tables connected to it, like a star. - Building Relationships: connecting tables together using a shared column (e.g., product_id in both the sales table and the products table) - Cardinality: describes how rows relate between two tables — "one-to-many" means one product can appear in many sales rows, but each sale points to only one product - Cross-Filter Direction: controls which table's filters affect the other when you click on a chart

A Simple Example A sales fact table has columns: date, product_id, customer_id, amount. It connects to a products dimension table (with product names, categories) and a customers dimension table (with names, cities) — each linked by their shared ID column. This is a simple star schema.

🧠 Now You Try (Exercise) On paper, sketch a star schema for a school: one fact table for "test results" (student_id, subject_id, score), connected to two dimension tables — one for students, one for subjects. Draw the connections.

✅ Big Idea to Remember A messy or missing data model is the #1 reason beginners get confused, wrong, or duplicated numbers in Power BI. Get the model right first — everything downstream depends on it.

🧮 Lesson 5: Introduction to DAX

Let's start simple DAX (Data Analysis Expressions) is Power BI's own formula language — similar in spirit to Excel formulas, but built specifically to work across your entire data model, not just individual cells.

Key Ideas - DAX formulas always start by naming what you're creating, followed by = - Unlike Excel, DAX formulas are aware of your whole data model — filters, relationships, and all

A Simple Example A very first DAX formula, calculating total sales:

Total Sales = SUM(Sales[Amount])

This single line can now be dragged into any chart, and it will automatically recalculate correctly no matter how the report is filtered — by region, by date, by product, anything.

🧠 Now You Try (Exercise) In plain English, describe what you think Total Sales = SUM(Sales[Amount]) is doing, based on what you already know about SQL's SUM() function from Part 3.

✅ Big Idea to Remember DAX feels intimidating at first because it looks like a new language — but it borrows heavily from ideas you already know from Excel formulas and SQL aggregate functions.

📐 Lesson 6: Calculated Columns, Measures & Common DAX Functions

Let's start simple DAX gives you two different ways to add new calculations to your model, and knowing which one to use is one of the most important beginner skills in Power BI.

Key Ideas - Calculated Column: creates a new column of data, calculated row by row, and stored permanently in your table (uses more memory) - Measure: calculates a result on the fly, based on whatever is currently being viewed/filtered — much more flexible and efficient, and the one you'll use most often - CALCULATE(): one of the most powerful DAX functions — lets you change the filter context of a calculation (e.g., "total sales, but only for 2025") - Time Intelligence Functions: built-in functions for comparing across time, like "sales this year vs. last year"

A Simple Example A measure calculating sales just for Lagos:

Lagos Sales = CALCULATE(SUM(Sales[Amount]), Sales[Region] = "Lagos")

This measure will automatically update if you add it to a chart that's already filtered by date or product — DAX handles all of that filtering logic for you.

🧠 Now You Try (Exercise) Without writing real code, describe in plain English what a measure called 2025 Sales = CALCULATE(SUM(Sales[Amount]), YEAR(Sales[Date]) = 2025) would calculate.

✅ Big Idea to Remember When in doubt, use a Measure rather than a Calculated Column — measures are more flexible, use less memory, and automatically respect whatever filters are applied to your report.

📈 Lesson 7: Building Reports & Visualizing Data

Let's start simple Now that your data is modeled and your DAX measures are ready, it's time to actually build the report — the visual page people will interact with.

Key Ideas - Report types: single-page summary reports, multi-page detailed reports, or paginated (print-style) reports - Drag fields and measures directly onto the canvas to create visuals — bar charts, line charts, cards (single big numbers), maps, and tables - Slicers: interactive filters that let the viewer explore the data themselves (e.g., a dropdown to pick a specific region)

A Simple Example You build a report with a big "Total Sales" card at the top, a bar chart of sales by region below it, and a slicer letting the viewer pick a specific year — instantly, every visual on the page updates together.

🧠 Now You Try (Exercise) Sketch (on paper) a simple one-page report layout for a school — what 3 visuals would you include, and where would you place each one?

✅ Big Idea to Remember A great Power BI report isn't just charts on a page — it's an interactive experience where the viewer can click, filter, and explore the data themselves, without needing you there to explain it.

🎯 Lesson 8: Dashboard Design & Data Storytelling in Power BI

Let's start simple Remember our earlier lessons on Dashboard Design Principles and Data Storytelling from Part 1? Now it's time to actually apply them, using everything Power BI gives you.

Key Ideas - Apply the same rules: keep it simple, use color with purpose, put the most important number top-left, align everything neatly - Use titles and short text boxes to guide the viewer through the story you're telling — don't just present charts and leave people to guess - Group related visuals together, and use consistent colors across the whole report

A Simple Example Instead of a page full of unlabeled charts, a well-designed Power BI report has a clear title ("Q3 Sales Performance"), a short summary sentence at the top ("Sales grew 12% this quarter, driven by Lagos"), and charts arranged to support that one central message.

🧠 Now You Try (Exercise) Look back at your Lesson 7 sketch. Add one sentence at the top of your sketched report that summarizes the "story" you'd want that report to tell someone in 5 seconds.

✅ Big Idea to Remember A technically correct report that tells no clear story still fails at its real job. Every report should have one central message the viewer walks away remembering.

🚀 Lesson 9: Publishing & Sharing

Let's start simple A Power BI report sitting only on your own laptop is exactly like the "hidden project" problem we talked about earlier — nobody else can see it or use it! Publishing is how you make your work truly usable by others.

Key Ideas - Power BI Service: the online platform where you publish reports so others can view them through a web browser, without needing Power BI installed - Data Refresh Schedules: setting your report to automatically pull in new data on a schedule (e.g., every morning at 6am), instead of manually refreshing forever - Dashboards vs. Reports: a report is a detailed, multi-visual page you build; a dashboard is often a simpler, pinned summary of your favorite visuals from one or more reports, for quick daily monitoring

A Simple Example You build a sales report and publish it to the Power BI Service. You set it to refresh automatically every morning at 6am, so by the time your manager checks it at 9am, the numbers are already up to date — without you doing anything.

🧠 Now You Try (Exercise) Write 2-3 sentences describing why a published, auto-refreshing report is more valuable to a real employer than a beautiful report that only exists on your personal laptop.

✅ Big Idea to Remember Just like your earlier GitHub lesson taught you: the work isn't finished when it's built — it's finished when it's published, shared, and visible to the people who need it.
