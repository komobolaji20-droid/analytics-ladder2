Lesson 1: Introduction to SQL

Excel is like organizing a small personal bookshelf, great for a few hundred rows. Once you have millions of rows, you need something bigger: a database. SQL, or Structured Query Language, is how you talk to a database and ask it questions.

Data lives in tables, the same shape as our snack shop's spreadsheet from Parts 1 and 2. Every column needs a clear, consistent name, and every column has a type: text, number, date. SQL enforces this strictly. A query is simply a question you ask the database, written in SQL. Different databases, like MySQL, PostgreSQL, and SQL Server, speak slightly different dialects, the way British and American English differ, but the core is the same everywhere.

Let's put our snack shop into a real database table called snacks, with the same four rows we've used from the start:

SELECT name, type, price, units_sold
FROM snacks
WHERE units_sold > 10;

In plain English: "Show me the name, type, price, and units sold from the snacks table, but only where units sold is more than 10." Run against our shop's data, that returns Chin Chin, Coke, and Fanta, and leaves out Meat Pie, since its 8 units don't clear the bar of 10.

Now you try it

  1. Without running any code, what would this query return using our shop's data: SELECT name, price FROM snacks WHERE price < 200;?
  2. Rewrite the original query in this lesson to instead return snacks where units_sold is less than 15. Which rows would come back this time?
  3. Would WHERE units_sold > 10 and WHERE units_sold >= 10 return the same rows from our table, or different ones? Why?

The takeaway

SQL queries always follow the same basic shape: SELECT what you want to see, FROM which table, WHERE which conditions. Everything else you learn in this part builds on this one pattern.

Lesson 2: Writing SQL Well

Now that you can write a basic query, it's worth learning to write them clearly, correctly, and in a way that's easy to fix when something breaks.

SQL runs your query in a specific order behind the scenes, not top to bottom like a story, which is part of why debugging can feel confusing at first. Reading error messages carefully, checking spelling of table and column names, and testing small pieces of a query at a time all help. Style matters too: capital letters for SQL keywords, lowercase for your own table and column names, with clear indentation.

Here's the same question about our shop, written two ways. Messy: select * from snacks where units_sold>10 and type='Snack'. Clean:

SELECT *
FROM snacks
WHERE units_sold > 10
  AND type = 'Snack';

Both return the same answer, just Chin Chin in our four-row table, but the second version is far easier for you, or anyone else, to read and fix six months from now.

Now you try it

  1. Rewrite this messy query in good style: select name,price from snacks where type='Drink'.
  2. Run your cleaned-up version against our shop's data mentally. Which two snacks come back?
  3. What's one specific thing that becomes harder to spot in the messy, one-line version compared to the clean, multi-line version?

The takeaway

Good SQL isn't just about getting the right answer. It's about writing queries you, and others, can still understand months later.

Lesson 3: Filtering and Comparison

Filtering narrows a huge table down to just the rows you care about, like using a sieve to separate what you want from everything else.

The comparison operators are =, >, <, >=, <=, and != for not equal. Text needs quotes, so WHERE type = 'Snack' works but WHERE type = Snack doesn't. NULL means no value at all, and you can't check it with = NULL; you need IS NULL or IS NOT NULL instead. And CASE is SQL's version of an IF statement, for building categories on the fly.

Let's grade our snack shop's items by how well they're selling:

SELECT name,
  CASE
    WHEN units_sold >= 15 THEN 'Strong seller'
    WHEN units_sold >= 10 THEN 'Steady seller'
    ELSE 'Needs attention'
  END AS performance
FROM snacks;

Run against our four rows, Chin Chin and Coke come back as "Strong seller," Fanta as "Steady seller," and Meat Pie, with only 8 units, as "Needs attention," the exact same flag Excel's conditional formatting gave it back in Part 2.

Now you try it

  1. Using the CASE statement above, which category would a fifth snack land in if it sold exactly 10 units?
  2. Write a WHERE clause that filters our table down to only snacks priced at ₦150 or less. Which snacks come back?
  3. If our shop's table had a notes column and some rows didn't have anything written there, what SQL condition would find just those empty rows?

The takeaway

Filtering is where SQL starts to feel powerful. You can ask specific questions of huge tables in just a few lines, the same way our CASE statement instantly flagged Meat Pie without you scanning the table by eye.

Lesson 4: Summarizing Data

Just like Excel's Pivot Tables, SQL has its own way of turning many rows into a handful of meaningful summary numbers.

COUNT, SUM, AVG, MIN, and MAX are the core aggregate functions. GROUP BY groups rows that share a value so you can summarize per group. WHERE filters before grouping, AS renames a result column, and ORDER BY arranges your results.

Let's ask the same question we answered with a Pivot Table back in Part 2, Lesson 5: total units sold, grouped by type.

SELECT type, SUM(units_sold) AS total_units
FROM snacks
GROUP BY type
ORDER BY total_units DESC;

Against our table, this returns Drink with 32 units (20 Coke plus 12 Fanta) ahead of Snack with 23 units (15 Chin Chin plus 8 Meat Pie), sorted highest first. Notice this is the exact same answer the Pivot Table gave you, just written as SQL instead of dragged with a mouse.

Now you try it

  1. Write a query that finds the average price per type instead of the total units. What average does Snack show versus Drink?
  2. Add a WHERE clause to only include rows where units_sold is above 10, before grouping by type. Does Meat Pie's row get included in this version?
  3. Compare your GROUP BY answer for total units per type to the Pivot Table result from Part 2. Do they match exactly?

The takeaway

Whenever you want an answer "per group," per type, per customer, per day, you're reaching for GROUP BY alongside an aggregate function like SUM or AVG. It's the same instinct as a Pivot Table, expressed in code.

Lesson 5: Joins

Real databases rarely keep everything in one table. Our shop, for instance, might keep snack details in one table and each day's sales in another. A JOIN combines them back together to answer a question that needs both.

Tables are usually linked by a shared column, an ID that appears in both. An INNER JOIN returns only rows that match in both tables. You can join three or more tables in a single query, and UNION stacks two tables' results on top of each other rather than joining them side by side.

Let's split our shop's data properly. A snacks table holds snack_id, name, type, and price. A sales table holds sale_id, snack_id, and units_sold, one row per day per item. To see snack names next to their sales:

SELECT snacks.name, sales.units_sold
FROM snacks
JOIN sales ON snacks.snack_id = sales.snack_id;

This reconnects the two tables using snack_id, giving you back the exact same combined view we've been working with as one table all along, except now the snack details and the sales figures can be updated independently, and each snack can have many days of sales attached to it.

Now you try it

  1. Why might a real shop want to keep snacks and sales as two separate tables instead of one big table like we've used through Parts 1 and 2?
  2. If the sales table had three rows for Meat Pie (one per day, say 8, 5, and 10 units), what would SUM(sales.units_sold) return for Meat Pie after joining the two tables and grouping by name?
  3. What would happen if a row in sales referenced a snack_id that didn't exist in the snacks table? Would an INNER JOIN include that row or leave it out?

The takeaway

Joins are the heart of working with real databases. Almost no useful business question, including every question we've asked about our own snack shop, can be answered from just one table alone once the data grows realistic.

Lesson 6: Subqueries and CTEs

Sometimes answering one question requires the answer to a smaller question first. A subquery is a query written inside another query, a question inside a question.

A subquery can sit inside a WHERE clause or a SELECT clause. A correlated subquery depends on the outer query and runs once per row. A Common Table Expression, or CTE, is a cleaner way to write complex queries, using WITH to name a temporary result you can reuse. CTEs are usually easier to read and debug than deeply nested subqueries.

Let's find which of our snacks sold above the shop's average. Our four units-sold values, 15, 20, 8, and 12, average out to 13.75.

SELECT name, units_sold
FROM snacks
WHERE units_sold > (SELECT AVG(units_sold) FROM snacks);

That inner query calculates 13.75, and the outer query then returns only rows above it: Chin Chin at 15 and Coke at 20. The same logic, written as a CTE instead:

WITH avg_sales AS (
  SELECT AVG(units_sold) AS avg_units FROM snacks
)
SELECT name, units_sold
FROM snacks, avg_sales
WHERE units_sold > avg_units;

Now you try it

  1. Walk through the subquery version step by step: what does the inner query calculate first, and what does the outer query do with that result?
  2. If Meat Pie's units_sold increased from 8 to 20, would the average used in the inner query change? Would that change which snacks qualify in the outer query's result?
  3. Which version, the subquery or the CTE, would you rather read again six months from now? Why?

The takeaway

When a question needs an answer within an answer, like "above average" needing the average calculated first, reach for a subquery or CTE. As logic gets more complex, CTEs usually stay easier to follow.

Lesson 7: Window Functions

Sometimes you want to compare each row to a group, like ranking each snack's sales within its own type, without collapsing the individual rows into one summary. That's exactly what window functions do.

RANK() and ROW_NUMBER() assign a rank to each row. A sliding window or frame looks at nearby rows, useful for something like a 7-day moving average. PARTITION BY restarts a calculation for each group instead of running it across the whole table.

Let's rank our snacks by units sold, but separately within each type:

SELECT name, type, units_sold,
  RANK() OVER (PARTITION BY type ORDER BY units_sold DESC) AS rank_in_type
FROM snacks;

Within Drink, Coke ranks 1 and Fanta ranks 2. Within Snack, Chin Chin ranks 1 and Meat Pie ranks 2. Every row keeps its own line in the result, unlike GROUP BY, which would have collapsed Drink into one row and Snack into another.

Now you try it

  1. What would change in the query above if you removed PARTITION BY type entirely? Would Coke still rank 1?
  2. If a fifth snack, another Drink, sold 25 units, where would it rank among the Drink group?
  3. In your own words, what's the difference between what GROUP BY gives you and what a window function with PARTITION BY gives you, using our snack shop as the example?

The takeaway

Window functions let you compare each row to a group without losing any individual rows. Think of it as GROUP BY that keeps every row visible instead of collapsing them.

Lesson 8: Functions for Manipulating Data

Just like Excel has text and date functions, SQL has its own toolbox for cleaning and reshaping data directly inside the database.

Common data types include INT for whole numbers, DECIMAL for numbers with decimals, VARCHAR for text, and DATE. String functions like UPPER() and LOWER() change case, and SUBSTRING() pulls out part of a piece of text. Date functions extract parts of a date, like the year or month, from a timestamp.

Remember the messy text problem from Part 2, Lesson 3, where "Meat Pie" showed up with extra spaces and inconsistent capitalization? SQL solves it the same way Excel did:

SELECT UPPER(TRIM(name)) AS clean_name
FROM snacks;

This strips extra spaces and forces uppercase, so "meat pie" and " Meat Pie" both become "MEAT PIE," matching correctly instead of being miscounted as two different snacks, the exact bug we worked through with PROPER and TRIM back in Excel.

Now you try it

  1. If our sales table had a sale_date column, what SQL function from this lesson would extract just the year from it?
  2. Write a query that returns every snack's name in all lowercase, using a function from this lesson.
  3. Compare UPPER(TRIM(name)) in SQL to PROPER(TRIM(A2)) in Excel from Part 2. What's the same, and what's different, about how the two tools solve the same problem?

The takeaway

SQL isn't just for retrieving data. It has a full toolbox for cleaning and reshaping messy text, dates, and numbers right inside the query itself, the same jobs you first solved with formulas back in Excel.

Lesson 9: Creating and Managing Tables

So far, every lesson asked questions of data that already existed. SQL can also build and manage the tables themselves.

CREATE TABLE defines a new table and its columns. Column constraints are rules, like NOT NULL meaning a value can never be empty, or UNIQUE meaning no two rows can share it. A PRIMARY KEY uniquely identifies each row, an ID number no two rows share. INSERT INTO adds rows, UPDATE changes existing rows, ALTER TABLE changes the table's structure, and DELETE removes specific rows while DROP TABLE removes the whole table.

Let's finally create our snack shop's table properly, from scratch:

CREATE TABLE snacks (
  snack_id INT PRIMARY KEY,
  name VARCHAR(50) NOT NULL,
  type VARCHAR(20) NOT NULL,
  price DECIMAL(6,2),
  units_sold INT
);

INSERT INTO snacks VALUES (1, 'Chin Chin', 'Snack', 200, 15);
INSERT INTO snacks VALUES (2, 'Coke', 'Drink', 150, 20);
INSERT INTO snacks VALUES (3, 'Meat Pie', 'Snack', 300, 8);
INSERT INTO snacks VALUES (4, 'Fanta', 'Drink', 150, 12);

UPDATE snacks SET units_sold = 10 WHERE name = 'Meat Pie';

That last line updates Meat Pie's units_sold from 8 to 10, exactly the kind of change that would happen if a correction came in after the fact.

Now you try it

  1. Why does snack_id make sense as the PRIMARY KEY here, rather than name? Think back to the "coke" versus "Coke" typo problem from earlier lessons.
  2. Write an ALTER TABLE statement that would add a new column called notes to the snacks table.
  3. If you ran DELETE FROM snacks WHERE name = 'Meat Pie';, how many rows would remain in the table? What if you ran DROP TABLE snacks; instead?

The takeaway

Every table you've ever queried started with a CREATE TABLE statement, designed with intention. Good table design, like giving our shop's snacks a proper snack_id, makes every future query easier and prevents the exact mismatches that caused problems back in earlier lessons.
