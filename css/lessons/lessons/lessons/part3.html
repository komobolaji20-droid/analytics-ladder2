🗄️ Lesson 1: Introduction to SQL

Let's start simple Imagine a library with millions of books. Excel is like organizing a small personal bookshelf — great for hundreds of rows. But when you have millions of rows, you need something bigger: a database. SQL (Structured Query Language) is how you "talk" to a database and ask it questions.

Key Ideas - Tables: data is stored in tables, just like Excel — rows and columns - Field naming: each column needs a clear, consistent name (e.g., customer_name, not "Column1") - Data types: every column has a type — text, number, date — and SQL enforces this strictly - Writing Queries: a query is simply a question you ask the database, written in SQL - SQL "Flavours": different databases (MySQL, PostgreSQL, SQL Server) speak slightly different dialects of SQL — like British English vs. American English. The core is the same.

A Simple Example The most basic SQL query looks like this:

SELECT customer_name, amount
FROM sales
WHERE amount > 1000;

In plain English: "Show me the customer name and amount, from the sales table, but only where the amount is more than 1000."

🧠 Now You Try (Exercise) Without running any code yet, write out in plain English what this query would ask for:

SELECT product_name, price
FROM products
WHERE price < 500;

✅ Big Idea to Remember SQL queries always follow the same basic shape: SELECT (what you want to see) FROM (which table) WHERE (which conditions). Almost everything else you learn builds on this one pattern.

🛠️ Lesson 2: Intermediate SQL

Let's start simple Now that you can write a basic query, let's talk about writing them well — clearly, correctly, and in a way that's easy to fix when something goes wrong.

Key Ideas - Querying a database: connecting to real data and running your questions against it - Query execution: SQL runs your query in a specific order behind the scenes (it doesn't read top to bottom like a story!) — understanding this helps you debug faster - Debugging SQL: reading error messages carefully, checking spelling of table/column names, and testing small pieces of your query at a time - SQL style: writing in capital letters for SQL keywords (SELECT, FROM, WHERE) and lowercase for your own table/column names, with clear indentation — this makes queries much easier to read later

A Simple Example A messy, hard-to-read query:

select * from sales where amount>1000 and region='Lagos'

The same query, written with good style:

SELECT *
FROM sales
WHERE amount > 1000
  AND region = 'Lagos';

Both do the exact same thing — but the second one is much easier for you (or anyone else) to read and fix later.

🧠 Now You Try (Exercise) Take the messy query above and try rewriting it in good style yourself, with capital keywords and clean spacing, before checking it against the example.

✅ Big Idea to Remember Good SQL isn't just about getting the right answer — it's about writing queries that you (and others) can still understand six months from now.

🔎 Lesson 3: Filtering & Comparison

Let's start simple Filtering is how you narrow down a huge table to just the rows you actually care about — like using a sieve to separate what you want from everything else.

Key Ideas - Comparison Operators: =, >, <, >=, <=, != (not equal) - Filtering Numbers: WHERE age > 18 - Filtering Text: WHERE country = 'Nigeria' — text needs quotes! - NULL handling: NULL means "no value at all" — you can't use = NULL, you must use WHERE column IS NULL or IS NOT NULL - CASE Statements: SQL's version of an IF statement, for creating categories on the fly:

SELECT name,
  CASE
    WHEN score >= 70 THEN 'A'
    WHEN score >= 50 THEN 'B'
    ELSE 'F'
  END AS grade
FROM students;

A Simple Example Finding all customers from Nigeria who spent more than ₦5,000, and haven't provided a phone number yet:

SELECT *
FROM customers
WHERE country = 'Nigeria'
  AND amount_spent > 5000
  AND phone IS NULL;

🧠 Now You Try (Exercise) Write a CASE statement that labels any score above 80 as "Excellent," scores 50-80 as "Good," and anything below 50 as "Needs Improvement."

✅ Big Idea to Remember Filtering is where SQL starts to feel powerful — you can ask incredibly specific questions of huge tables in just a few lines.

📊 Lesson 4: Summarizing Data

Let's start simple Just like Excel's Pivot Tables, SQL has its own way of turning thousands of rows into a handful of meaningful summary numbers.

Key Ideas - Aggregate Functions: COUNT(), SUM(), AVG(), MIN(), MAX() - GROUP BY: groups rows that share a value, so you can summarize per group (e.g., total sales per region) - Summarizing Subsets: combining WHERE (filter first) with GROUP BY (then summarize) - Aliasing: renaming a column in your results using AS, e.g., SUM(amount) AS total_sales - Sorting: ORDER BY — arranging your results, e.g., biggest to smallest

A Simple Example "What's the total sales per region, from highest to lowest?"

SELECT region, SUM(amount) AS total_sales
FROM sales
GROUP BY region
ORDER BY total_sales DESC;

🧠 Now You Try (Exercise) Write a query (on paper) that finds the average score per subject from a students table with columns subject and score, sorted from highest average to lowest.

✅ Big Idea to Remember Whenever you want an answer "per group" (per region, per subject, per customer), you're reaching for GROUP BY alongside an aggregate function like SUM or AVG.

🔗 Lesson 5: Fundamental SQL — Joins

Let's start simple Real databases rarely keep everything in one giant table — instead, information is spread across multiple related tables (customers in one table, their orders in another). A JOIN is how you combine them back together to answer a question that needs both.

Key Ideas - Defining relationships: tables are usually linked by a shared column, like customer_id - INNER JOIN: brings back only rows that match in both tables - Multiple Joins: combining 3 or more tables together in a single query - UNION / UNION ALL: stacks two tables' results on top of each other (instead of joining them side-by-side) — useful when combining similar data from two sources, like sales from 2024 and sales from 2025

A Simple Example Finding customer names alongside their orders (two separate tables, joined together):

SELECT customers.name, orders.amount
FROM customers
JOIN orders ON customers.customer_id = orders.customer_id;

🧠 Now You Try (Exercise) Imagine two tables: students (student_id, name) and scores (student_id, subject, score). Write out in plain English how you'd join them to see each student's name next to their scores.

✅ Big Idea to Remember Joins are the heart of working with real databases — almost no useful business question can be answered from just one table alone.

🪆 Lesson 6: Subqueries & CTEs

Let's start simple Sometimes, to answer one question, you first need the answer to a smaller question. A subquery is a query written inside another query — like a question inside a question.

Key Ideas - Subqueries: a query nested inside another query's WHERE or SELECT - Correlated Subqueries: a subquery that depends on the outer query, running once for every row - Nested Subqueries: subqueries inside subqueries - Common Table Expressions (CTEs): a cleaner, more readable way to write complex queries, using WITH to name a temporary result you can reuse - CTE vs. Joins/Correlated Subqueries: CTEs are usually easier to read and debug for complex, multi-step logic

A Simple Example Finding customers who spent more than the average customer, using a subquery:

SELECT name, amount_spent
FROM customers
WHERE amount_spent > (SELECT AVG(amount_spent) FROM customers);

The same idea, written more readably with a CTE:

WITH avg_spend AS (
  SELECT AVG(amount_spent) AS avg_amount FROM customers
)
SELECT name, amount_spent
FROM customers, avg_spend
WHERE amount_spent > avg_amount;

🧠 Now You Try (Exercise) In plain English, explain what the subquery example above is doing, step by step — starting with the inner query first.

✅ Big Idea to Remember When a question needs an answer within an answer, reach for a subquery or CTE — and once your logic gets complex, CTEs almost always keep things more readable.

🪟 Lesson 7: Window Functions

Let's start simple Sometimes you want to compare each row to a group — like "rank each student's score within their own class" — without collapsing all the individual rows into one summary. This is exactly what window functions are built for.

Key Ideas - Ranking Functions: RANK(), ROW_NUMBER() — assigns a rank to each row - Sliding Window / Frames: calculations that look at a "window" of nearby rows (e.g., the last 7 days) - Moving Average: an average that updates as you move through the data — useful for smoothing out noisy trends - Paging: splitting results into pages, useful for showing "Top 10" style results - Pivoting: reshaping rows into columns (or vice versa) for reporting

A Simple Example Ranking students by score within each class:

SELECT name, class, score,
  RANK() OVER (PARTITION BY class ORDER BY score DESC) AS class_rank
FROM students;

This gives every student a rank — but restarts the ranking for each class, thanks to PARTITION BY.

🧠 Now You Try (Exercise) In plain English, describe what would change in the example above if you removed PARTITION BY class entirely.

✅ Big Idea to Remember Window functions let you compare each row to a group, without losing any of the individual rows — think of it as "GROUP BY, but keeping every row visible."

🔤 Lesson 8: Functions for Manipulating Data

Let's start simple Just like Excel has text and date functions, SQL has its own toolbox for cleaning and reshaping messy data directly inside the database.

Key Ideas - Common Data Types: INT (whole numbers), DECIMAL (numbers with decimals), VARCHAR (text), DATE - Date & Time Functions: retrieving the current timestamp (NOW() or CURRENT_TIMESTAMP), extracting parts of a date (YEAR(), MONTH()) - String Functions: changing text case (UPPER(), LOWER()), parsing string and character data (SUBSTRING()) - Working with Arrays: some databases let a single column hold a list of values, and searching within them - Numeric Functions: rounding, and using numeric data with summary functions like SUM and AVG

A Simple Example Standardizing messy names to a consistent format:

SELECT UPPER(TRIM(customer_name)) AS clean_name
FROM customers;

This removes extra spaces and makes every name uppercase, so " bolaji" and "Bolaji" both become "BOLAJI" — matching correctly instead of being treated as different values.

🧠 Now You Try (Exercise) Write a query (on paper) that extracts just the year from an order_date column, so you could later count how many orders happened per year.

✅ Big Idea to Remember SQL isn't just for retrieving data — it has a full toolbox for cleaning and reshaping messy text, dates, and numbers right inside the query itself.

🏗️ Lesson 9: Creating and Managing Tables

Let's start simple So far, we've focused on asking questions of existing data. But SQL can also build and manage the tables themselves — this is where you go from "user of a database" to someone who truly understands how it's built.

Key Ideas - CREATE TABLE: defines a brand new table and its columns - Column Constraints: rules on a column, like "this can never be empty" (NOT NULL) or "this must be unique" (UNIQUE) - The Key to a Database: a PRIMARY KEY uniquely identifies each row — like an ID number no two people share - INSERT INTO: adds new rows of data - UPDATE: changes existing data - ALTER TABLE: changes a table's structure (like adding a new column) - DELETE vs. DROP TABLE: DELETE removes specific rows; DROP TABLE removes the entire table completely - Temporary Tables: tables that exist only for the current session, useful for breaking a complex problem into smaller steps

A Simple Example Creating a simple table for students:

CREATE TABLE students (
  student_id INT PRIMARY KEY,
  name VARCHAR(100) NOT NULL,
  score DECIMAL(5,2)
);

INSERT INTO students VALUES (1, 'Bolaji', 85.5);

UPDATE students SET score = 90 WHERE student_id = 1;

🧠 Now You Try (Exercise) On paper, design a simple table for tracking books in a small library: what columns would you need, and which one would you make the PRIMARY KEY?

✅ Big Idea to Remember Every table you've ever queried started with a CREATE TABLE statement, designed with intention — good table design makes every future query easier.
